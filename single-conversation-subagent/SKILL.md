主对话负责用户交互、阶段记忆、直接派发和最终验收。子 Agent 只分析、实现或测试，不再委派。MCP 记录交互、状态和证据，不调度 Agent。

**ZCode 使用宿主注册身份。** 侦察、实施、验证、设备/现场验证分别派 `查询侦察员`、`实施工程师`、`测试验证员`、`设备与端到端验证员`；正式审查只派 `固定审阅员`。用 `Agent(subagent_type=<准确角色名>)`，沿用角色的模型和权限。下文把它们称为执行角色和审阅员；其他宿主仍用各自的执行角色和 `codex-review`。ZCode 启用 `SCS_NATIVE_REVIEW=1`。

## 开场

1. 项目根用用户明确指定的目录，否则用当前对话工作目录。模式和根已明确就开始会话绑定；只有缺少信息时，做至多一次直接相关的只读查询。开场确认以前先不做任务排查、构建、串口或设备操作。ZCode 从宿主角色注册表核对 `固定审阅员`；其他宿主核对 `codex-review`。有则 `registered`，明确无则 `unregistered`，未知则 `unknown`。同时核对宿主实际生效的七个角色工具集与 `zcode-agents/permissions.json`：超出矩阵（例如顾问可写、审阅员可执行命令）时停止该角色派发并按真实原因登记，不按正文声明假设只读。
2. `session_open` 传项目绝对路径、宿主真实 conversation_id（有才传）和已核实的 `review_registration`。首次用户只说「不用问，直接做」时，附 `explicit_skip=true` 进入快速模式。项目元数据和索引可写时传 `register_obsidian=true`，建库并登记给 PyQt。已有选择直接沿用。保留 session_id 和原 client_name；同一会话重连或补登记时用 `resume_session_id` 和原项目根恢复。ZCode 核对返回 `native_review=true`；服务未启用时先说明配置，普通角色仍可按宿主权限使用，正式审查按原生方式手工记录。MCP 不可用时用原生问答或文本确认，主对话保留证据。
3. 模式未定时问快速处理 / 标准执行 / 长任务 / 只调查，推荐一个。用户已明确选模式时，以 `interaction_request(kind="mode", channel="text")` 和真实选择 `interaction_submit` 直接登记。沿用已确认模式，显式切换用 `interaction_reopen(explicit_user_change=true)`。
4. **开始实现、执行测试或派发前完成开场确认**。标准/长任务先问验证范围并确认写入。现场验证选 `journey`，在建包的 `test` 子任务定义中声明 `execution_profile=journey`。
   - **ZCode 长任务只确认收尾审查**。验证范围后用 `codex_gate` 问「仅收尾审查」或「不做独立复核」，记录 `closure` 或 `none`。通常推荐集中收尾审查。历史 `packages` 只沿用其收尾选择。其他宿主沿用各自的复核选项。
   - **标准或快速确认收尾是否请固定审阅员**。核实审阅员已注册后提问，使用 `codex_review` 提交 `yes` 或 `no`。只调查、审阅员可用性未知或未注册时跳过。
   - **长任务必做方案指导**：ZCode 确认长任务、验证范围和复核策略后，先由主对话调用一次 `Agent(subagent_type="方案顾问")`。选择长任务即进入这项只读指导，无须再弹一个同意框。简报包含目标、允许范围、候选方案、风险、验证和回滚。等实际完成回执，将建议与需要用户决策的事项纳入协调记录，再拆工作包和派执行角色。同一任务继续或恢复时沿用已交回的方案指导；角色不可用或未完成时，报告受阻并先解决缺项。选择「不做独立复核」的长任务也要派方案顾问。
   - **高危短任务方案指导**：用户同意后可派一次 `方案顾问`，高危操作仍另走预审和确认。其他宿主沿用原有 Codex 方案指导规则。方案意见、操作预审与正式审查分别保存。
   - **收尾审查**：实现和验证完成后，按已选策略和下文冻结规则独立派审阅员。ZCode 新开 `Agent(subagent_type="固定审阅员")`，只读核对范围、证据和现状，保存宿主返回的实际 Agent ID 和原始最终消息。已选收尾审查须有绑定当前范围、含唯一 `结论: ACCEPT` 的完成回执，或用户对当前范围的有效 `WAIVED`，才能通过该审查门槛。

## 逐题交互

- 原生路径（ZCode 默认）：`interaction_request(channel="native")` 返回 `NATIVE_QUESTION_REQUIRED` 时，立即调用宿主原生问答工具。用返回的简短 `display_text` 和 `options.label` 提问，将推荐项置顶并标明。提交时用对应的 `options.value`。登记状态本身不证明已显示。等到用户实际回答，再用原 `question_id` 调 `interaction_submit`；**看到 `CONFIRMED` 才请求下一题**。没有原生工具时，使用同一题的文本回退。
- 文本路径：展示完整 `display_text`，结束当轮等待明确回复，然后用同一题号提交。每次只用一路提问。收到 `QUESTION_PENDING` 时处理返回的原题；如果用户已答就补提交，否则继续等待。需要重试已结束的题时，按用户明确要求重开。取消、拒绝、失败和默认勾选均不确认选择。
- MCP form 是配置为 mcp 或 auto 且支持表单时的回退。仅 `interaction_ask` 使用服务端 15 秒截止。按已告知的超时策略处理，`TIMED_OUT` 不写确认。无 form 或无回通道时用同一题号走原生或文本。原生/文本不声称 15 秒。详见 [MCP 用法](references/mcp.md)。
- 推荐理由一句话，最多 160 字。首次用 `workspace_scan` 辅助判断范围，不把扫描全文回传到每道题。上下文压缩时只保留会话 ID、项目根、已确认选择、待答题号、工作包修订、下一步和证据路径；按需读取详细状态。

## 长任务执行

长任务模式服务于整个交付，不要求每个小步骤都走完整流程。用强模型做一次方案指导和已选的独立审查，把有实际工作量的实施和验证交给执行角色。方案一旦足够开工，优先派发已就绪的工作；不为补齐流程再开一轮侦察。仅阻塞环节等授权或依赖，独立工作继续。

- **小改不另起流程（有累计上限）**：目标、范围已明确且低风险的单点小改、只读核对、日志摘要或证据更正，可由主对话直接处理并做必要自检，或并入当前实施任务。代码小改仅限冻结前、同一工作包同一验收目标累计一次、一个既有文件、一个 diff hunk、增删合计 ≤10 行且无行为变化；主对话记录理由、基线和受影响路径。出现第二个文件或 hunk、行为或断言变化、构建/回归、启停服务、连续现场取证、计划内设备交互时，必须先 `work_attempt_prepare` 再派角色。仍遵守当前工作包范围、已选审查和资源限制；不得在同范围有活动 attempt 时抢写。
- **用户旅程验收**：UI、App 或用户可见交付必须包含现场旅程——在用户实际使用的 URL/服务实例/设备上执行「入口 → 主操作 → 可见结果」，记录路由、实例/构建标识、设备、时刻、动作、实际结果、关键断言和必要截图。主对话完成授权与单项 prepare，派 `设备与端到端验证员`（其他宿主使用具备等效能力的获授权角色）执行并提交证据，随后抽核关键证据并验收。长驻 dev server 先观察原实例，再在刷新或新页面对照，保留刷新前观测；不可达时记 `NOT_RUN`/`BLOCKED`，不用冷启动测试代替现场验收。
- **按需委派和并行**：入口不明才派 `查询侦察员`；有实际工作量的修改交 `实施工程师`；固定命令验证交 `测试验证员`；ADB/串口/烧录/浏览器等现场工作交 `设备与端到端验证员`。按可独立验收的结果建包，文件范围列实际改动及审查所需路径，不把 `build/` 等产物目录放进源码复核范围。同批最多 4 个就绪的独立任务；共享串口、板卡、写范围和其他独占资源串行，不为凑并发拆小任务。职责与模型见 [roles.md](references/roles.md)；子 Agent 不再委派或发起正式审查。
- **先占后派**：`work_attempt_prepare` 或单包批量的 `work_attempt_prepare_many` 成功后再启动宿主 Agent；批量全有或全无，同批依赖按波次准备。结果用 `work_attempt_update` / `work_attempt_update_many` 串行登记，`operation_id` 保证重试幂等。长执行可用 `work_attempt_note` 追加审计备注（不改版本、不续租、不证明存活），用 `run_map` 查看有界 JSON/Mermaid。
- **ZCode 包级复核：用户点名，轮次由用户确认**。只在用户本轮明确要求复核指定工作包时，先根据项目风险、范围和交付阶段询问“本次计划几轮、是否作为收尾审查”并记录；等包内静止后调用 `work_attempt_prepare(subtask_id="review", user_requested=true)`。每次新增轮次都必须由用户在当前交互明确确认，不自动重试；启动失败或中断消耗当轮。收到成功回执才派 `固定审阅员`；brief 写清受支持入口、输入契约、非目标输入和 findings 格式，只有可达且违反契约/验收条件的发现可作为阻塞项。保存当前 `review_subject`、真实 Agent ID 和 [原生回执](references/mcp.md#zcode-固定审阅员回执)。包级回执只记录该次判断；是否作为关包条件由用户本轮决定（默认不作为门槛），实质问题仍按原验收处理。其他宿主沿用原协议。
- **先汇报交付，再处理复核差项**：阶段结果一经核实就告诉用户，分别写清产物、实测结果和工作包复核状态。仅范围元数据或证据摘要有误时，优先用原始证据修订，仅重跑受影响或证据失效的验证。工作包应声明受支持入口、输入契约和非目标输入；审阅员 findings 带 `severity` 与 `reachability`，只有可达且违反契约/验收条件的阻塞项才进入修正。审查退回后，对有明确范围和证据的阻塞项默认只自动做一轮修正、必要验证和复审；收尾沿同一整改链最多两次自动派发（含中断/无效回执），切修订不重置。按修订计数的两次自动派发仅适用于非原生 `packages` 的包级复核。ZCode 手动包级轮次由用户确认；到限聚合全部 findings 交用户决策，不自动创建下一轮。尚未满足已选复核条件的包保留真实状态。详见 [复核退回与证据复用](references/protocol.md#复核退回与证据复用)。
- **收尾审查冻结**：从派发前冻结到回执核对和最终验收结束。派发前确认所有相交包的写入和设备 attempt 静止，保存 `closure_subject`（包身份、修订、各包指纹、集成文件快照、验收契约、带包身份的必验项、重读原件的哈希、现场实例及产物标识）。期间禁止相交写入和设备操作。收回回执和最终验收前重算，快照不完整则保持未通过，发现中途变化即登记 `STALE` 并作废本轮覆盖，即使末态摘要恢复。整改前保留原回执、登记 `STALE`，开新修订或后继包，再 prepare → 派实施或设备角色 → 必要验证 → 新审查或用户明确豁免。证据摘要笔误可追加勘误并保留原件和指纹。
- **静止与终态**：有活动 attempt 时不得 `REVIEW_READY`、`COMPLETED`、`ABANDONED`、切修订或 handoff。验收通过用 `COMPLETED`、重复或被取代用 `ABANDONED`，两类终态都必须写 `close_reason`，关闭后不可修改。

工作包、并发、证据和交接详见 [完整协议](references/protocol.md)。

## 破坏性操作闸门（全模式）

- **日常开发板烧录**：仅在能核实目标是指定开发／测试板、实际只更新可回刷的应用固件分区、不改引导／分区／OTA 状态或安全配置、不覆盖或清除持久数据，且有可用回刷路径时，免独立预审和闸门登记。执行前由主对话说明目标板、拟执行命令、写入范围与回刷方式，并取得针对这次烧录的明确授权；验证范围、默认选项和「继续」不等于授权。
- **高风险刷写**：整片擦除、写引导程序／分区表／OTA 状态／安全配置、可能丢失持久数据、生产设备，或目标／实际写入范围／可恢复性不明时，走完整闸门。按命令实际可能写入的范围判断，不以 `flash` 命令名或本次预计跳过的段判断；同一被 REJECT 的方案不得改称日常烧录继续执行。
- 删除/覆盖用户数据或系统关键配置、高风险刷写、drop 数据库/表、不可逆 git 操作、递归 `chmod`/`chown`、卸载关键包、`allowed_files` 之外的大范围改写等，必须走完整闸门：主对话准备命令/`cwd`/目标/影响面/备份/回滚 → 审阅员只读预审 → `operation_gate_record` → 执行前 `operation_gate_check` 为 `APPROVED`，并保留用户独立确认。ACCEPT 需报告唯一结论 + `user_confirmed=true`；ZCode 先用实际参数 `operation_gate_check` 取得 `operation_digest`，派 `固定审阅员`，登记时提交对应的 v2 `review_receipt`；REJECT 对同 `operation_id`/digest 是终态，不可覆盖；审阅员不可用只能记 `UNAVAILABLE_OVERRIDE`，不得伪记 ACCEPT。普通代码编辑、证据写入和视图刷新不触发。

MCP 不执行、不拦截宿主命令；没有宿主 Hook 时这是协议级约束（`PROTOCOL_ONLY`），不是执行级强制。详见 [烧录分类与完整流程](references/protocol.md#破坏性操作闸门)。

## ZCode 子 Agent 上下文判断

用户问子 Agent 上下文占用，或主对话准备 `SendMessage` 续跑已结束的子 Agent 时，由主对话查宿主记录：先调用 `ListModels`，再运行 [只读上下文探针](references/zcode-context.md)，用目标子会话最近一次请求的用量和该子 Agent 实际 `provider/model` 的窗口计算。不要借用主对话模型窗口，也不要按轮数、累计账单或缓存未命中数估算。

只有原工作线、角色、基线和授权仍相容，且探针给出 `REUSE`，才允许考虑续跑；长任务仍先 prepare 新 attempt。`ROTATE` 或 `UNKNOWN` 时不续旧实例，需要继续就新开同角色，只带必要交接。包级复核、正式收尾和操作预审仍独立新开 `固定审阅员`，不受占用比例影响。

## 执行与收尾

快速由主对话直接处理；只调查保持只读，范围大时可派只读子 Agent。标准执行由主对话按计划实现和执行常规验证，现场旅程沿用上述授权、单项 prepare 与派发规则，收尾按已确认的选择派审阅员。长任务按上节四角色与复核策略执行。子 Agent 继承主对话的授权和验证范围。未选的测试标 `NOT_RUN`；不做测试与只记录方法互斥，均不标 PASS。主对话核对关键证据并抽核执行角色提交的用户旅程证据后验收，省略全量日志。

docs-root 优先 00_doc / 00_docs / docs / doc，均无则用 docs。项目与协作记忆、证据在其 agent/，审查报告在 04_test/report/。MCP 初始化缺失记录，主对话维护审查记录；恢复前核对 SQLite 与手工记录。PyQt 可直接打开已登记的库，视图刷新和故障处理见 [Obsidian 视图](references/obsidian.md)。
